# 文档生命周期管理 — Agent 开发 SOP

## 背景

项目因持续积累一次性分析文档、调试记录、实施报告导致文件膨胀。**14 个文档** 在一次清理中被删除。

## 核心原则

> Documentation should describe the project, not the development process.

## A→E 分类法

| 类别 | 示例 | 处理 |
|------|------|------|
| **A. 永久文档** | README, DATABASE.md, CLAUDE.md | 保留，随项目更新 |
| **B. 长期记录** | ADR、架构变更 | 保留到 `docs/history/` |
| **C. 一次性分析** | `*-analysis.md`, `*-audit.md` | **立即删除** |
| **D. 实施报告** | 普通功能报告 | **删除**（重大升级才保留）|
| **E. 临时文件** | server.log, *.bak, *.tmp | **立即删除** |

## 目录规范

```
docs/
├── architecture/     # 永久设计文档
├── history/          # 长期记录（ADR、重大变更）
└── development/      # 开发规范、规则
```

## 在编写知识库/文档时的原则

### 1. 区分「事实」和「过程」

| 值得保留 | 不值得保留 |
|---------|-----------|
| API 设计、数据库 schema | 某次修复的具体步骤 |
| 架构决策及其理由 | 某次调试的输出日志 |
| 性能指标、基准值 | 某次 benchmark 的原始数据 |
| 数据流、状态图 | 某次实施过程中的中间状态 |

### 2. 每个知识库文件应该有独立价值

- 能回答一个常见问题
- 能避免后来者踩同一个坑
- 能解释一个「为什么是这个方案」

### 3. 不要保留的信息

- 命令行的历史输出
- 一次性的 debug 分析
- 非结论性的探索记录
